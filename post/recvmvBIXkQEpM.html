你抛弃的n8n工作流，Claude Code捡回来了，但最让我意外的不是这个

关注 「林月半子的AI笔记」，设为「星标」

我是林月半子，教你用AI干掉90%的重复劳动！

去年 n8n 很火，我平时的工作流基本都是拿它搭的，甚至给客户定制了不少智能体。后来随着 Skills、Hermes 这些 AI 原生方案越来越成熟，我自己的个人工作流已经逐步迁移过去了，n8n 主要留给企业项目。

前几天刷推的时候发现 Claude Code 居然支持了 /workflows，作为工作流的古早玩家，这必须试试。

然后我就拿手头一个一直想重构的项目开刀了。

先说说 /workflows 是什么

简单来说，/workflows 就是你给 Claude Code 一个目标，它自己现场编排出一套执行方案，然后调度一堆子智能体分工跑完。不是你提前画好流程让它照着走，而是它自己规划、拆解、执行，一条链路跑到底。

你可以把它理解成 n8n 的 AI 原生版，不用拖节点、不用配连线，你用自然语言描述流程，它自己编排执行。

这个功能目前是研究预览版，Pro 用户在 /config 里打开就能用，需要 Claude Code v2.1.154 或更高版本。

我试了一下，确实能跑，具体效果后面会看到。

但今天这篇的重点不是 /workflows。

试完之后我顺手就拿 Claude Code 干了点正事，手头有个老项目一直想重构，正好趁这个机会搞一搞。跑这些任务时底层用的模型，才是真正让我意外的。

我拿什么项目来试？

我之前做过一个插图 Skill，专门用来给技术文章生成插图。核心逻辑是调用不同的图片生成 API（我管它叫 provider），根据文章内容自动出图。

生成逻辑我用 Python 脚本写的，没有全做成 .md 配置，主要是方便 debug，脚本出问题可以直接跑、直接调。

项目跑了挺久，但有个问题一直困扰我：所有 provider 的逻辑全塞在一个文件里。A平台、B平台、X平台，全挤在一起，代码越来越臃肿，每次加新 provider 都要在一堆 if-else 里面找位置。

任务一：重构 Provider 架构

直接在 Claude Code 里下了一条指令：

分析当前项目中 ./skills/linyuebanzi-image-gen/scripts/generate.py的代码结构。这个文件里所有provider的逻辑全部挤在一起，我需要你做一次完整的重构：1.先通读整个项目，理解现有的架构和每个provider的差异2.把通用逻辑（HTTP请求、轮询等待、错误处理）抽成一个base模块3.每个provider拆成独立文件，只保留自己特有的逻辑（请求构造、响应解析、payload构建）4.创建一个工厂函数统一调度，主入口generate.py只负责调度5.确保重构后所有provider 的功能跟之前完全一致，包括环境变量读取、默认配置、轮询逻辑

这个任务考验的不是"能不能写代码"，任何模型都能写代码。关键是它能不能理解现有的代码架构，搞清楚哪些逻辑是通用的、哪些是各 provider 独有的，然后规划出一个合理的拆分方案。这是典型的 Agent 任务：需要先分析、再规划、再执行，不是一句话就能搞定的。

然后它开始跑了。

它自己把这个重构拆成了 3 个子任务：
1. Create providers package with base class and 3 provider implementations
2. Refactor generate.py to use the new provider modules
3. Verify refactored code works correctly

4 分 19 秒，跑完了整个重构。

重构前：generate.py 一个文件，693 行，所有 provider 的逻辑用 if/elif 分支混在一起。

重构后：主入口 generate.py 只剩调度逻辑，每个 provider 独立一个文件，通用逻辑抽到 base 模块。职责清晰，加新 provider 再也不用翻几百行代码找位置了。

693 行的大杂烩拆成了 6 个职责单一的文件，架构一目了然。

但重构只是第一步。代码写完了，谁来 review？

我把这个重构提了一个 PR，然后让 Claude Code 的 /workflows 来做 code review。

它直接启动了一个 multi-agent review workflow，5 个 agent 分 5 个阶段依次跑：Architecture Review、Bug Hunt、Parity Check、Code Quality、Synthesis。

每个 Agent 各司其职。

有的专门审架构设计，有的专门找 bug，有的专门做行为一致性校验。而驱动这 5 个 Agent 的底层模型，全部都是 Step 3.7 Flash。

5 个 Agent 跑完之后，还真让它揪出了一个 critical bug——重构的时候 run_single() 函数的签名改了，但调用处传参没跟着改，导致 --aspect-ratio 和 --resolution 两个 CLI 参数被直接丢弃了。单张模式下永远用默认值 16:9 / 2K，CLI 传什么都没用。

除了这个 critical bug，它还列了一张完整的问题清单——--provider 的 choices 硬编码了、BaseProvider 没用 abc.ABC + @abstractmethod、异常类型不一致……从 Critical 到 Info 分了四个等级，条理很清楚。

我直接说了句"修复一下吧"，它不光修了那个 critical bug，把 Medium 和 Low 级别的问题也全部修完了。最后给了一张修复总结表，7 个问题修了 6 个，剩下 1 个 Info 级别的标注了"设计层面，暂不改动"。

四笔提交，所有 review 发现的问题都修完了，PR 干干净净。

这个过程让我印象很深，重构本身跑得很顺，但 review 环节还是抓到了遗漏。一个 Agent 写代码，另外 5 个 Agent 审代码，审完直接修，互相兜底。

这才是 multi-agent 的真实价值。

而驱动这一切的，都是同一个 Flash 级别的模型。

真正让我意外的是这个

看到这里你可能觉得，Claude Code 用的是 Claude 自家的模型，这效果好也正常。

其实不是。

我跑这个重构任务的时候，底层模型用的是阶跃星辰的 Step 3.7 Flash。

没错，不是 Claude Sonnet，不是 Opus，是一个 Flash 级别的模型。

Step 3.7 Flash 是阶跃星辰面向生产级 Agent 场景专门优化的模型。它不是那种"跑个 benchmark 分数好看"的模型，而是真的在 Agent loop 里——规划、搜索、工具调用、代码生成、多轮修正——每一步都做了效率优化。

开源、可本地部署，而且是 Flash 级别的成本。

任务二：看图说话——多模态扩充插图风格

重构搞定了，接下来换个维度，我们来试试 Step 3.7 Flash 的多模态能力。

我平时刷技术博客的时候，偶尔会看到一些插图风格特别好看的文章，就顺手把图存下来。存多了之后就想，能不能把这些风格也加到我自己的插图 Skill 里？

不过在干活之前，我先想确认一个事：Step 3.7 Flash 作为一个 Flash 级别的模型，它的图片理解能力到底怎么样？

分析得还挺准的——配色方案、线条风格、构图特点、质感、整体氛围，每个维度都拆得很细。不是那种泛泛的"这是一张手绘风格的图"就完事了，它能具体到"手绘素描风，线条有轻微不规则抖动""背景有细微纸张纹理，增加手绘真实感"这种程度。

行，识图能力没问题，那就让它干正经活吧。

我的这个插图 Skill 目前支持 6 种插图风格，每种风格都有一个 .md配置文件，定义了 prompt 模板和视觉参数。

styles/
├── cartoon-infographic.md
├── cozy-handdrawn.md
├── executive-tech.md
├── infographic.md
├── notebook.md
└── tech-doodle.md

我想再扩充一种新风格，但手动写 prompt 模板太费劲。你得精确描述配色、线条、构图、质感，还得确保生成出来的图跟你脑子里想的一样。

所以我就把刚才那几张参考图放到项目目录里，让 Step 3.7 Flash 自己搞定所有的事。分析图片风格、生成 prompt 模板、读懂项目结构、改好所有需要改的代码。

简单来说就是：你先看看现有风格文件怎么写的，再读一遍项目代码搞清楚加一种新风格需要动哪些地方，然后分析参考图、起个名字、把所有改动一步到位。

1 分 31 秒，全部搞定。

不光分析了风格、生成了 prompt 模板，还自己判断出需要改哪些文件，一次性全改完了。

整个过程就是丢几张图进去，它自己搞定剩下所有的事，不用额外配视觉 MCP 或者其他什么东西。

两个任务跑完，我的感受

说实话，跑之前我对 Flash 级别的模型没抱太大期待。

之前听到"Flash"这个词，下意识觉得就是"便宜版""能用但糙"。但实际跑下来，它在 Agent 场景里的表现完全不糙——代码重构的架构理解到位，多模态的图片风格分析也准确，而且都能自己判断需要改哪些文件、怎么改。

而且速度确实快。两个任务跑下来，整个流程的响应很流畅，没有那种"等半天才出结果"的感觉。对于 Agent 这种需要多轮调用的场景，每一步快一点，累积下来体验差异很大。

当然也不是一步到位的。

重构那个任务，first-pass 写出来的代码结构没问题，但 5 个 Agent 审完还是揪出了 1 个 critical bug 和 6 个中低级问题。不过话说回来，发现 bug 的是 Step 3.7 Flash，修 bug 的也是 Step 3.7 Flash——5 个 Agent 分工审查，7 个问题修了 6 个，全是同一个 Flash 模型干的。互相兜底，最终交付的代码质量是过关的。

对于 Agent 场景来说，Flash 级别的成本才是能在生产环境里用得起的。一个 Agent 任务跑下来可能调几十次模型，如果每次都是旗舰模型的价格，很多场景根本撑不住。Step 3.7 Flash 刚好卡在"用得起 + 搞得定"这个位置。

再加上开源可部署，对于做企业项目的人来说，客户经常要求数据不出内网，这一点很实际。

写在最后

工作流这个东西，形态一直在变。从 Zapier 到 n8n，从拖拽到自然语言，从单模型到 multi-agent。

但核心没变过，你定义目标，机器去执行。

变的只是"执行"这件事，越来越不需要你操心了。

Claude Code 的 /workflows 是一个信号。

而 Step 3.7 Flash 让我看到，驱动这一切的，不一定非得是最贵的模型。

够快、够稳、用得起。

在 Agent 时代，这三个字可能比"最强"更重要。

Step 3.7 Flash 是开源的，感兴趣的可以搜一下阶跃星辰。
